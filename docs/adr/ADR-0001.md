# ADR-0001: Remove the word-detection seam (`IWordDetector` / `WordDetector`)

- **Status:** Accepted
- **Date:** 2026-08-27
- **Decided in:** architecture review (Candidate 1 — the false word-detection seam)

## Context

An architecture review of the Counting Engine found that `WordCounter` injected `IWordDetector` but
never invoked it; production word counting used `string.Split` (classic `wc` token semantics).
`WordDetector` (185 lines) and its tests were dead — the tests were commented out and no production
code called the detector. The seam had exactly one implementation, making it a *hypothetical seam*
(one adapter = hypothetical, two = real). The CLI Contract fixes word counting to wc-compatible
token counting, so the detector's "looks like a word" logic would have changed behaviour if wired in.

## Decision

Delete `IWordDetector` and `WordDetector` (and the dead `WordDetectorTests`). `WordCounter` owns
wc-token counting directly via `string.Split`. The reusable library does **not** expose a pluggable
word-definition seam.

## Consequences

- Word definition is concentrated in `WordCounter` — a single source of truth that matches the CLI Contract.
- The library loses pluggable word detection. This is acceptable: `wc` token counting is the only contract.
- Tests now back the real path: `WordCountContractTests` pins wc-token semantics (e.g. `---` and `don't!`
  each count as one word), replacing the deleted false-confidence tests.

## Revisit clause

Future architecture reviews should **not** re-suggest making word detection a pluggable interface unless a
genuine second word-definition implementation is needed (which would make the seam real, not hypothetical).
